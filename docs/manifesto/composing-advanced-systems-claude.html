Your Next Level

From Single Tools to Enterprise Systems

You learned to build a brick. Now learn to build the wall — and see the path from wall to building to city. This is your guide to composing tools into real business workflows, explained for someone who thinks in systems, not syntax.
In Your Foundation, you learned every line of a single tool — how data shapes flow through a 3-line orchestrator, how the brain stays pure and the adapters handle the messy real world. You saw where it stops: one tool can't talk to another.

This document solves that problem. It also shows you the full arc — from where you are now to an agentic MIS/ERP system that enterprises pay for. The gap is real, the timeline is real, and starting now is the single smartest move you can make.
Part One

Why Good Bricks Aren't Enough

You have an order_quote tool that calculates pricing. You have an invoice_generator tool that produces PDFs. Each is perfectly built — clean contracts, pure logic, comprehensive tests. Each works flawlessly in isolation.

Now a client says: "When a customer submits an order, I need pricing calculated, credit checked, and an invoice generated automatically."

Three tools need to talk to each other. How hard could it be? Here's the naive approach:

quote = order_quote.run(order_input)Step 1: Calculate pricing
invoice_input = InvoiceInput(Step 2: Manually wire the output to the next input
customer=quote.customer_name,Copy this field
line_items=quote.items,Copy that field
total=quote.total_cents,Copy this one too
)
invoice = invoice_generator.run(invoice_input)Step 3: Generate the invoice
Looks fine. What's wrong?

You just hardwired the output shape of tool A directly into the input of tool B. If order_quote renames customer_name to customer, this script breaks — and so does every other place these tools connect.

Worse: What if the quote returns an error? This code crashes. What if the credit check says "denied" — do we still generate the invoice? What if we need to insert a fourth tool between them later?

That 6-line script is the seed of the same concrete the first manifesto warned about. Except now it's growing between your tools instead of inside them.

The Business Analogy

Imagine you built three perfect departments: sales, credit, and billing. Each does their job brilliantly. But the "process" of moving an order through all three is a guy named Dave who walks paperwork between desks, translating by memory.

Dave knows that sales calls it "customer_name" but billing calls it "client." Dave knows the credit team needs the total in dollars, but sales outputs it in cents. Dave carries all of this in his head. When Dave quits, the process collapses.

The naive wiring code IS Dave. The composition discipline you're about to learn replaces Dave with documented, tested, replaceable translation layers.

The Glue Trap: Why 70% of Your Code Becomes Wiring

Research shows that roughly 70% of development effort in integrated systems goes to "glue code" — the wiring between components. Not because glue is hard, but because nobody plans it. Nobody designs it. Nobody tests it.

And here's the math that makes it terrifying:

The N-Squared Problem

5 tools that talk to each other = up to 25 connection points
10 tools = up to 100 connection points
20 tools = up to 400 connection points

Without discipline, the glue overwhelms the tools. You built 20 beautiful bricks and drowned them in sloppy mortar. An enterprise ERP might have 50+ tools. Without composition architecture, that's 2,500 potential connections. This is why enterprise systems cost millions and take years.

The Core Insight

Inside a tool, coupling comes from mixing decisions with plumbing. (You learned this.)

Between tools, coupling comes from mixing translation with orchestration. (This is new.)

Translation = converting one tool's output into another tool's input (mapping fields, transforming data).

Orchestration = deciding which tools run in what order and what happens when something fails.

When these two live in the same code, you get the same rigidity problem — just one level up. The solution is the same too: separate them.

Part Two

Translators: The Mortar Between Bricks

The first new concept is the translator. It's a pure function that converts one tool's output into another tool's input. Nothing more. Nothing less.

# translators.py — pure functions, no I/O, no flow logic
def quote_to_invoice_input(quote):Takes QuoteOutput, returns InvoiceInput
return InvoiceInput(
customer=quote.customer_name,Map this field to that field
line_items=[
InvoiceLineItem(
description=item.product_name,Quote calls it "product_name", invoice calls it "description"
quantity=item.qty,
unit_price_cents=item.unit_price_cents,
total_cents=item.line_total_cents,
)
for item in quote.itemsDo this for each item in the quote
],
subtotal_cents=quote.subtotal_cents,
tax_cents=quote.tax_cents,
total_cents=quote.total_cents,
)
What this does, in plain English

The quote tool says "customer_name." The invoice tool expects "customer." This function translates. The quote tool says "product_name." The invoice expects "description." This function translates.

It's exactly what Dave was doing by memory — except now it's written down, tested, and replaceable. When the quote tool changes its output, only this function changes. The invoice tool never knows. The flow runner never knows. Every other translator is untouched.

Key rules for translators:

• Pure function — no files, no web, no database. Just data in, data out.

• One direction only — quote-to-invoice is one function. Invoice-to-quote (if you ever need it) is a separate function.

• Independently testable — give it a QuoteOutput, check that you get the right InvoiceInput.

Why one direction only?

Think of a human translator at the UN. One translator handles English-to-French. A different translator handles French-to-English. They're different skills, different contexts, different edge cases.

If you build a single "bidirectional" translator, it becomes complicated, hard to test, and serves two masters. One-way translators are simpler, easier to test, and easier to replace.

Part Three

The Flow Runner: The Dumb Orchestrator, One Level Up

Inside a single tool, the orchestrator was 3 lines and had zero branching. Between tools, the same rule applies — the flow runner is a dumb recipe that calls tools and translators in order.

# flow.py — the dumb flow runner
def run_order_flow(order_input):The entire business process
steps = [A list of (name, tool, translator) tuples
("quote", order_quote.run, None),Step 1: calculate pricing
("credit", credit_check.run, quote_to_credit),Step 2: check credit (translate first)
("invoice", invoice_generator.run, quote_to_invoice),Step 3: generate invoice (translate first)
]
results = {}Track what each step produced
for name, tool_run, translator in steps:Walk through each step...
input_data = translator(prev) if translator else order_inputTranslate if needed
result = safe_run(name, tool_run, input_data)Run the tool safely
if isinstance(result, Err):If it failed...
return FlowResult.failed(step=name, completed=results)...stop and report what happened
results[name] = result.valueOtherwise, save the result and continue
return FlowResult.success(results)All done! Return everything.
What you're looking at

This is a for-loop over a list of steps. That's it. Under 20 lines. No business logic. No field mapping. No "if the credit is denied, do X." Just: run each step, translate between them, stop if something fails.

steps = [...] — The recipe. A list of 3-part instructions: what to call this step, which tool to run, and which translator to apply before running it. None means no translation needed (it's the first step, so it uses the original input).

for name, tool_run, translator in steps: — "Walk through each step. Unpack its name, its tool function, and its translator."

safe_run(name, tool_run, input_data) — Runs the tool and catches any errors, wrapping them in a result type (more on this next).

The constraint: Maximum 40 lines. Zero business logic. Zero data translation. Zero error recovery logic. If your flow runner grows past 30 lines, something has leaked in that belongs in a translator or a decision function.

Think of it like a project manager

A good project manager doesn't do the work. They don't write code, don't design graphics, don't close sales. They say: "First, sales prepares the quote. Then, give that to credit for review. Then, give it to billing for the invoice."

They don't translate between departments (that's the translator's job). They don't decide what to do about a denied credit check (that's a decision function). They just run the sequence.

If you find your project manager doing the actual work, something's wrong with your org structure. Same with the flow runner.

Every composed workflow gets its own directory, mirroring how tools are structured:

flows/order_to_invoice/One directory per workflow
  DECISIONS.mdWhat decisions does this FLOW make?
  models.pyFlowResult, FlowDecision shapes
  translators.pyPure functions: tool A output → tool B input
  decisions.pyPure functions: flow-level decisions
  flow.pyThe dumb flow runner (~20 lines)
  compensation.pyWhat to undo when steps fail
  tests/Tests for translators, decisions, and the flow
Part Four

Result Types & The Railway Pattern

Inside a single tool, if a function fails, Python throws an error and everything stops. Simple. But in a multi-tool flow, you need to know which step failed, what succeeded before it, and what might need undoing. Crashes aren't good enough.

The solution: every step returns a Result type — either Ok (success with a value) or Err (failure with a reason).

@dataclass
class Ok:"It worked. Here's the value."
value: objectThe actual result data
@dataclass
class Err:"It failed. Here's why."
error: strWhat went wrong
context: dictExtra info (which step, partial results)
In plain English

Instead of code that crashes when something goes wrong (losing all context), every step returns a labeled package: either "here's your result" (Ok) or "here's what went wrong and where" (Err).

@dataclass — just means "this is a data form." You learned this in Your Foundation.

value: object — The actual data. Could be a QuoteOutput, a CreditDecision, anything.

context: dict — A dictionary of extra information: which step failed, what partial results were produced before it, what inputs were used. Everything a human (or a compensation handler) needs to understand what happened.

This creates what's called the Railway Pattern. Visualize two tracks:

OK quote → translate → credit → translate → invoice → done!
⬇ diverts on failure ⬇
ERR credit denied → skip invoice → return failure with context
Two tracks, no branching

The flow rides the green track (Ok) as long as everything succeeds. The moment any step fails or a decision says "stop," the flow diverts to the red track (Err). No if statements in the flow runner. The Result type handles the branching automatically.

Why this matters for enterprise: When a client asks "what happened to order #4872?", you don't say "it crashed." You say "the quote succeeded ($1,080), the credit check returned 'review required,' and the invoice was never generated. The partial results are preserved. Here's exactly where it stopped and why."

That's the difference between amateur software and enterprise software. It's not about preventing failure. It's about handling failure with full visibility.

Part Five

Compensation: The Undo Button

Here's the hardest problem in composed systems: what happens when step 3 fails but steps 1 and 2 already did real-world things?

The credit check approved the customer. The payment was charged. Then the invoice generation fails. The customer was charged but never got an invoice. You need to undo the charge.

# compensation.py — what to undo when the flow fails
compensations = {For each step that touches the real world...
"charge_payment": lambda ctx: refund(ctx["payment_id"]),...define the reverse action
"send_invoice": lambda ctx: void_invoice(ctx["invoice_id"]),
"reserve_stock": lambda ctx: release(ctx["reservation_id"]),
}
def compensate(completed_steps, failed_step):Run undos in REVERSE order
for step in reversed(completed_steps):Last completed step gets undone first
if step in compensations:
compensations[step](completed_steps[step])Run the undo with the step's context
The beautiful payoff of pure tools

Here's where everything comes together. Remember: the tools in core/ are pure math. They don't charge payments, send emails, or write to databases. Only the adapters do real-world things.

So in a 5-step flow where 3 steps are pure computations and 2 steps are adapter calls, you only need 2 compensations, not 5. The pure steps produced data, not effects. Data doesn't need undoing.

This is why the first manifesto's rule — "side effects at the edges" — pays compound interest at the composition level. The fewer real-world effects your system produces, the less you need to undo when things go wrong. The more confidently you can compose complex flows.

Business analogy: the refund policy

A good business defines refund procedures before they sell the first product. Not after a customer complains. Not after the accountant discovers a discrepancy.

Compensation is your refund procedure for each step: if we charged the card, the undo is a refund. If we reserved inventory, the undo is a release. If we sent an email — well, you can't unsend it, so the compensation is a follow-up correction email.

The rule: every step that touches the real world must define its undo. This is written alongside the flow, not scattered across different files. And compensations must be idempotent — running them twice produces the same result as running them once (because in failure scenarios, you might accidentally trigger the undo more than once).

Part Six

Three Levels of Composition Testing

Inside a tool, you test that functions produce correct outputs. Between tools, you test something different: that tool A's output actually works as tool B's input, even though they know nothing about each other.

1
Translator Tests
"Given this QuoteOutput, does the translator produce the correct InvoiceInput?" Pure unit tests. Fast. Deterministic. Tests every field mapping.
2
Contract Compatibility Tests
Run tool A with real input. Pass the real output through the translator. Feed it to tool B. Does tool B accept it without error? This catches the subtle mismatches — like one tool using cents and another using dollars — that look fine in isolation but explode when connected.
3
End-to-End Flow Tests
Run the entire flow with realistic input. Verify the final output. Because all tools are pure math, these tests require no databases, no network, no files and run in milliseconds. You can test a 5-tool enterprise workflow as easily as testing a calculator.
The Catch That Only Level 2 Finds

The order_quote tool returns amounts in cents (integer: 10800). The invoice_generator expects amounts in dollars (float: 108.00). Both tools pass their own tests. But when composed, the invoice shows $10,800 instead of $108.00.

This is the impedance mismatch problem — the most common failure in composed systems. It's not a bug in either tool. It's a bug in the assumption that they're compatible. Level 2 tests catch this by running real outputs through real translators into real inputs.

When a tool changes its contract, the compatibility tests for every flow that uses it fail simultaneously. This is the desired behavior — you find all the breakage at once, not one at a time in production.

Part Seven

Growing a System Flow by Flow

Just like tools grow by adding files (not making files bigger), composed systems grow by adding flows (not making flows bigger).

Month 1: Order-to-Invoice
Build the first flow. 3 tools, 2 translators, 1 flow runner. It works. Ship it.
Month 2: Add Payment
Don't modify order-to-invoice. Build a NEW flow: invoice-to-payment. 2 tools, 1 translator. The original flow is untouched.
Month 3: End-to-End
Need order-to-payment? Build a NEW flow that composes the two existing flows. It calls order-to-invoice, then invoice-to-payment. One new translator. Both sub-flows untouched.
Month 4: Refunds
Build process-refund. New flow, new translators, new compensations. References the payment tool but through its own translator. All order flows untouched.
Month 6: A Real System
4 flows, 8 tools, 10 translators. Each flow is a directory. Each existing flow was never modified after it shipped. That's growth by addition — the same principle from the first manifesto, applied one level up.

Part Eight

The Vision: From Flows to Agentic ERP

Now let's zoom out. Way out. You've learned to build bricks (tools) and walls (flows). An enterprise MIS/ERP system is the building. And the emerging concept of agentic AI is what makes the building intelligent.

Here's where the industry is right now, and why your timing is right:

The State of Play (2025-2026)

78% of IT leaders expect ERP functionality to be replaced or augmented by agentic AI within 3 years. But only 23% have successfully scaled autonomous AI across operations. That gap is where the opportunity lives.

Gartner forecasts 40% of business applications will embed task-specific AI agents by end of 2026, up from under 5% in 2025. McKinsey identifies the core challenge: LLMs have been "fundamentally reactive and isolated from enterprise systems" — unable to retain memory, coordinate across sessions, or operate as persistent, embedded systems.

The companies that win will be the ones that solve composition — wiring AI agents into reliable, testable, compensable workflows. Sound familiar?

The Three Layers You're Building Toward

1
Tools Layer (Where You Are)
Individual business functions, each a Soft Code tool with pure logic, tested contracts, and clean adapters. Order pricing, credit checks, invoice generation, inventory lookups. These are your bricks.
2
Flows Layer (What You're Learning Now)
Composed workflows that wire tools together with translators, result types, and compensation. Order-to-invoice, procure-to-pay, forecast-to-plan. These are your walls.
3
Agent Layer (Where Enterprise Is Going)
AI agents that can select and orchestrate flows based on context. A customer support agent that decides: "this is a refund request" → triggers the process_refund flow. A procurement agent that: receives a purchase request → checks budget (tool) → finds vendors (tool) → creates PO (flow) → routes for approval (flow). The agent chooses the flows. The flows run the tools. The tools do the math.
The fractal pattern

Inside a function: separate decisions from plumbing.

Inside a tool: separate core from adapters.

Between tools: separate flows from translators.

Between flows: separate agent decisions from flow execution.

The same principle at every level. That's why learning it at the tool level gives you the mental model for every level above it. You're not learning one technique — you're learning the technique that scales to infinity.

What Makes an Agentic System Trustworthy

The industry is converging on five requirements for enterprise-grade agentic systems:

1
Observability
You can see exactly what every agent did, which flow it triggered, which tools ran, what data flowed between them. Because your tools produce plain data at every boundary, every step is inspectable. This is built into the architecture you're learning.
2
Human-in-the-Loop
Agents can handle routine decisions autonomously, but sensitive actions (large refunds, new vendor approvals, credit overrides) route to a human for approval. The flow runner already supports this — it's just a decision function that returns "needs_review" instead of "proceed."
3
Compensation & Rollback
When an agent-triggered workflow fails partway through, the system knows exactly what to undo. You're learning this now with compensation handlers.
4
Contract Testing
When an AI agent selects a flow, you need provable guarantees that the flow works correctly. The 3-level testing pyramid (translator tests, compatibility tests, end-to-end tests) gives you that proof. An enterprise client doesn't accept "it usually works." They accept "here are 147 passing tests."
5
Governance & Audit Trail
Every decision — by agent or human — is logged as a Result type with full context. "Agent selected process_refund flow. Credit check returned Ok. Payment refund returned Ok. Total processing time: 340ms." This is the audit trail regulators need.
The Current Gap — And Why It's Your Advantage

The gap between current AI and enterprise reality is real. LLMs make mistakes. They hallucinate. They lack persistent memory. They can't reliably coordinate across complex workflows — yet.

But here's the thing: the architecture doesn't depend on perfect AI. The tools are pure math — deterministic, tested, reliable. The flows are deterministic pipelines with explicit error handling. The AI agent layer sits on top, selecting which flows to run — and the human-in-the-loop catches its mistakes.

As LLMs get better, you loosen the human-in-the-loop constraints. You let the agent handle more autonomously. But the architecture underneath never changes. That's the whole point. You're building the foundation that makes AI useful today and powerful tomorrow.

The people who understand this architecture when LLMs reach enterprise capability will be the architects. Everyone else will be the users.

Part Nine

Same Repo or New Repo?

This is a practical question. The answer follows directly from the architecture:

Keep in the Same Repo
The tools layer (core/, adapters/) stays exactly where it is. No changes needed.

Add a flows/ directory at the repo root. Each composed workflow gets its own subdirectory with translators, decisions, flow runner, compensation, and tests.

Why: Flows depend on tool contracts. Keeping them in the same repo means contract compatibility tests can import directly from core/. When a tool changes, the flow tests fail immediately — in the same CI pipeline.
Separate Repo Later
When you have 15+ tools and 10+ flows, the repo may get large enough that a split makes sense.

At that point: tools become a library package with versioned contracts. Flows import tools via package version, not file path.

But not yet. Premature splitting creates more problems than it solves. Start in one repo. Split when the pain of a single repo exceeds the pain of managing two.

Part Ten

Your Roadmap

Phase 1: Master the Brick (Where You Are)
Build 2-3 more tools using the Soft Code workflow. Run preflight until everything passes. Get the discipline into your muscle memory. Use the code-reading trainer until you can read any tool in 3 minutes.
Phase 2: Build Your First Flow (Next)
Pick two tools that logically connect. Write the translator. Write the flow runner. Write the three levels of tests. Add a flows/ directory to your repo. Feel what it's like to compose tools without coupling them.
Phase 3: Add Compensation & Result Types
Build a flow that touches the real world (sends an email, writes a file). Implement compensation. Implement the railway pattern. Test failure scenarios. This is where you go from "it works" to "it works reliably."
Phase 4: Build a Real Business Workflow
Pick a real enterprise process: procure-to-pay, order-to-cash, or record-to-report. Build 4-5 tools and 2-3 flows that handle it end-to-end. This is your portfolio piece — the thing you show an enterprise client.
Phase 5: Add the Agent Layer
Build an AI agent that can select and trigger flows based on natural language input. "Process a refund for order #4872" → agent selects process_refund flow → flow runs tools → result returned with full audit trail. Human-in-the-loop for sensitive actions. This is the agentic ERP.
The Composition Checklist (Your New Preflight)
  • Before writing any composition code: Can I draw the tools as boxes and the data flows as arrows?
  • For each arrow, do I know what shape goes in and what comes out?
  • Have I identified which decisions belong to the flow (not to any tool)?
  • Have I identified which steps produce side effects that need compensation?
  • When writing translators: Is each one a pure function, one direction only?
  • Does each translator handle edge cases (None values, empty collections)?
  • When writing the flow runner: Is it under 40 lines?
  • Does it contain zero business logic and zero translation logic?
  • Does it use Result types at every tool boundary?
  • When testing: Level 1 translator tests? Level 2 compatibility tests? Level 3 end-to-end?
  • Do contract tests use real tool outputs, not hand-crafted fakes?
  • When handling failures: Are compensations defined for every side-effect step?
  • Are compensations idempotent and tested?
  • When growing: Am I adding a new flow directory, not modifying existing flows?
A Final Word

The manifesto said: "Decoupling is not an architecture you adopt once. It is a discipline you apply with every function, every file, every prompt you give to an LLM."

Composition extends that: the discipline applies with every tool, every translator, every flow.

The bricks are the tools. The mortar is the translators. The walls are the flows. Each material has its own discipline. A well-built wall requires well-made bricks, properly mixed mortar, and careful placement. Skip any one and the wall won't hold.

You have the business instinct. You have the architectural mental model. You have the discipline framework. And you're learning it at the exact right moment — before the industry figures out how to do this at scale.

The people building the architecture now will be the ones the enterprise clients call. Everyone else will be bidding on the scraps.
